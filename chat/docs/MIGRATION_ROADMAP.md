**0-6이 왜 앞에 있나**

**0단계에서 사장님이 정할 것** (BUILD_VS_BUY §8)
1. **iOS 전략**
   - 이유: Apple 1.2는 "random or anonymous chat … do not belong on the App Store"라고 원문으로 확인했다.
   - 권장: iOS는 출시하지 않고 Android·웹 먼저. iOS는 친구·방 중심 앱으로 따로 기획.
2. **중동 음성**
   - 이유: UAE는 VoIP가 TDRA 허가 사업이다.
   - 권장: UAE는 출시하지 않거나 글 전용. 사우디·카타르·이집트는 실측 후.
3. **랜덤 1:1 음성 도입 여부**
   - 지금은 070 결정으로 글만 된다.
   - 도입하면 SFU 경유와 레벨 2 인증이 필요하다.

## 3단계 — Control Plane 자체 운영

**시작 조건**(하나)
- Supabase 월 청구가 자체 최소 구성(약 $1,300) + 운영 인력비를 넘는다(대략 5천 CCU, COST_MODEL §5).
- Realtime 동시 연결이 1만을 넘어 Enterprise 계약이 필요해진다.

| # | 작업 | 검증 |
|---|---|---|
| 3-1 | 스테이징: Supabase 자체 호스팅(Docker Compose) + 운영 DB 덤프 복원 | `test_*.sql` 24개, 웹 Playwright 전체, Android e2e |
| 3-2 | 고가용·백업: Patroni(etcd 3) + pgBackRest(다른 업체 저장소) | 주 서버 강제 종료 → 자동 승격 시간, 복원 훈련 |
| 3-3 | 엣지 함수 13개를 자체 Deno 런타임(묶음 포함)으로, pg_net 웹훅 주소 교체 | 함수별 호출 |

**확인할 위험** [미확인]
- JWT 서명 키를 옮길 수 있나: 못 옮기면 전원 재로그인.
- `auth` 스키마 이전.
- Storage 객체 복사.
- Realtime 권한 정책 동작.
- → 3-1 스테이징에서 전부 확인한다.

## 4단계 — yaari-edge (매칭·presence·호출 제한)

**시작 조건**(하나)
- 0단계 뒤에도 DB CPU 60% 초과가 매칭·presence 때문이라고 측정된다.
- 매칭 대기 p95가 목표(3초)를 넘는다.

**작업**
- Go 서비스 하나 + Valkey.
- 매칭 규칙은 `find_match4`에서 그대로 옮긴다.
- 새 엔드포인트로 병행 운영하다가 옛 RPC를 지운다(헌법 5).

**검증**
- 경쟁 상태 테스트(같은 두 사람 동시 매칭 1,000회 → 중복 0)
- 차단·정지·검증 게이트 표 전부
- 부하 1k→25k

## 5단계 — 지역 확장

- **조건**: 해당 지역 사용자 10% 이상 + 실측 지연 문제.
- **순서**: 두바이/바레인(법률 확인 뒤) → 싱가포르 → 미국 동부.
- **방식**: 리전마다 LiveKit 2대~를 두고 토큰 서버가 리전을 선택한다.
- Control Plane은 늘리지 않는다. 다지역 DB는 쓰기 지연과 법이 요구할 때만 한다(TARGET §2-4).

## 하지 않는 것

- 자체 SFU를 처음부터 개발하지 않는다.
- 실측 병목 없이 마이크로서비스로 쪼개지 않는다.
- 모르는 사람 사이에 P2P를 쓰지 않는다.
- 스토어 결제를 우회하지 않는다.
- 부하시험 없이 "10만 지원"이라고 말하지 않는다.
- 무료라는 이유로 백업·암호화·접근 통제를 생략하지 않는다.
