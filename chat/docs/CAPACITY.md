# 동시접속 5만 명 — 서버가 버티는가 (2026-10-23 점검)

## 결론
- **지금 상태로는 5만 명을 못 버팁니다.** 동시접속 200명 근처에서 막힙니다.
- 가장 큰 원인은 코드가 아니라 **요금제 한도**입니다. Supabase가 무료 플랜이고, 실시간 연결이 최대 200개입니다.
- 5만 명을 받으려면 다음 세 가지가 함께 필요합니다.
  1. **요금제 상향**: Supabase Enterprise와 LiveKit Enterprise가 필요하고, 견적은 따로 받아야 합니다.
  2. **DB 서버 키우기**
  3. **실시간 구조 개선 (코드)**
- 실제 5만 명 부하 시험은 하지 않았습니다. 실서버를 쓰면 비용이 들고, 한도 때문에 바로 차단되며, 실사용자에게 영향이 갑니다. 아래 숫자는 측정값과 공식 문서 한도로 계산한 **추정**입니다.

**Supabase Postgres Changes (DB 변경을 실시간으로 보내는 방식)**
- 변경 하나마다 구독자 수만큼 권한 검사를 합니다.
- 단일 스레드로 처리되므로 DB 서버를 키워도 거의 빨라지지 않습니다.
- RLS를 켠 상태의 상한은 대략 초당 3,000–4,000건입니다.
- 공식 권장: 같은 변경을 구독하는 사람이 3,000명을 넘으면 Broadcast로 바꿀 것.

## 5만 명이 몰리면 생기는 일 (가정과 계산)

**가정**: 랜덤채팅 2만 명(그중 영상 1만 명), 보이스룸 2만 명, 둘러보기 1만 명

1. **실시간 연결**
   - 대부분의 사용자가 실시간 연결을 1개씩 엽니다. 약 5만 개가 필요합니다.
   - 무료 200, Team 10,000 → **Enterprise가 아니면 불가능**합니다.
2. **보이스룸 접속 확인(3초마다)**
   - 2만 명 ÷ 3초 = 초당 약 6,700회 호출입니다.
   - 회당 4–6ms로 잡으면 DB CPU가 초당 27–40초 필요합니다. 즉 **CPU 약 30–40코어**가 이 일에만 쓰입니다.
   - 8XL(32 vCPU) 이상이 필요하고, 그래도 다른 일과 겹치면 부족합니다.
3. **채팅 메시지**
   - 2만 명이 10초에 1개씩 보내면 초당 2,000건입니다.
   - Postgres Changes의 RLS 상한(초당 3,000–4,000건)에 바로 닿습니다. 보이스룸 채팅과 알림까지 더하면 넘칩니다.
4. **영상·음성 (LiveKit)**
   - 영상 1만 명 + 보이스룸에서 말하는 사람·듣는 사람 → 동시 연결이 수만 개입니다.
   - Scale 플랜 한도는 5,000개라 **Enterprise 계약이 필요**합니다.
   - 사용량 비용은 1만 명이 한 시간 영상통화하면 60만 분입니다. 분당 $0.0004로 계산하면 **약 $240/시간**(대역폭 요금 별도)이고, 상시 5만 명이면 월 수만 달러 규모입니다.
5. **번역(Anthropic)**
   - 메시지마다 번역하면 호출이 초당 수천 건입니다. API 속도 제한과 비용을 따로 잡아야 합니다.
   - Haiku로 회당 약 $0.0002라도 초당 2,000건이면 시간당 약 $1,440입니다.

## 코드 개선 (출시 전에 해 두면 좋은 순서)
1. **채팅·알림 실시간을 Postgres Changes에서 Broadcast로 전환**
   - 메시지 저장 트리거가 `realtime.send`로 해당 대화방 채널에만 보내게 합니다.
   - 보이스룸은 이미 Broadcast를 씁니다(0.8.0). 같은 방식을 DM·랜덤채팅·알림에 적용하는 것입니다.
2. **보이스룸 접속 확인 부하 줄이기**
   - 3초 하트비트를 DB가 아니라 Realtime Presence나 LiveKit 참가자 이벤트로 판단합니다. DB에는 30–60초에 한 번만 기록합니다.
   - "7초 뒤 연결 끊김" 동작은 그대로 유지할 수 있습니다.
3. **실시간 연결을 필요한 화면에서만 열기**
   - 둘러보기만 하는 사용자는 연결을 열지 않습니다. 연결 수가 크게 줄어듭니다.
4. **실제 부하 시험**
   - 스테이징 프로젝트(Supabase 브랜치)에서 k6 등으로 1천→5천→1만 단계로 시험합니다.
5. **번역 캐시**
   - 같은 문장 + 같은 언어는 한 번만 번역합니다. 상대가 번역 보기를 눌렀을 때만 번역합니다.

## 지금 서버 상태 [실행]
- Supabase 무료 요금제, DB Micro(최대 연결 60).
- 실시간 연결 한도 200개라서 **동시접속 약 200명에서 막힙니다**.

## 요금제별 실시간 한도 [문서]
- 무료: 연결 200
- Pro: 연결 500
- Pro(지출 한도 해제)·Team: 연결 10,000, 초당 메시지 2,500
- 10만 명: **Enterprise 계약**이 필요합니다.
- LiveKit Cloud도 Scale 요금제 상한을 넘으니 Enterprise가 필요합니다.

## 보안
- 067에서 고침: 로그인 안 한 사용자(anon)가 실행할 수 있던 함수 11개를 막았습니다(057·059). 실제 유출은 없었습니다 [실행].
- 이상 없음 [실행]
  - public 테이블 57개 모두 행 단위 보안(RLS)이 켜져 있습니다.
  - JWT 검증을 끈 edge function들은 각자 인증합니다.
  - 메시지·신고·댓글·방 비밀번호에 속도 제한이 있습니다.
- 남은 것
  - 매칭(`find_match3`)과 보이스룸 접속 확인(`voice_heartbeat3`)에 호출 속도 제한이 없습니다.
  - CSP의 `script-src 'unsafe-inline'`이 넓습니다.
  - 유출 비밀번호 차단 설정이 꺼져 있습니다(이 앱은 전화 인증만 써서 영향은 적습니다).

## 먼저 터지는 순서와 해결책
1. **실시간 연결 200개 (지금 당장)** → 요금제 상향. Team으로 1만 명까지, 10만 명은 Enterprise.
2. **DB 연결 60개, Micro CPU** → 컴퓨트 상향.
3. **보이스룸 3초 접속 확인** → 코드 개선. Realtime Presence나 LiveKit 웹훅으로 판단하고, DB에는 30–60초마다만 기록합니다. 효과가 가장 큽니다.
4. **알림 수 30초 조회** → Broadcast로 바꿉니다.
5. **방 목록·친구 상태·채팅 따라잡기** → Broadcast로 바꾸고, 따라잡기 주기는 60초로 늘립니다. 방 목록 1,000개 상한은 페이지 나누기로 바꿉니다.
6. **메시지 전달(Postgres Changes, 단일 스레드)** → 보이스룸처럼 트리거에서 `realtime.send`로 보냅니다.
