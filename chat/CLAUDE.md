# 랜챗(Yaari) 작업 방식 — 하자·슬롭 방지

0.18.4–0.18.6에서 효과음 하나를 추측으로 세 번 고치다 매번 다른 곳이 깨졌다. 같은 일이 다시 없도록 아래 순서를 지킨다.

## 1. 원인을 확정하기 전에는 코드를 고치지 않는다
- 증상을 재현하거나(데모 웹을 Playwright로, Android는 Robolectric 테스트로), 재현이 안 되면 **근거를 직접 읽는다**: 우리 코드의 실제 흐름, 라이브러리 소스·바이트코드(`~/.gradle/caches`의 aar → `javap -c`, `node_modules`), 플랫폼 소스(AOSP).
- "아마 이거겠지"로 고친 커밋 금지. 커밋 메시지·보고에 원인과 근거(파일·줄)를 쓴다.

## 2. 상태가 바뀌는 기능은 표부터 그린다
- 기능이 다른 상태(오디오 모드, 네트워크 연결, 권한, 백그라운드, 로그인)를 건너면 **모든 경우를 표로**: 처음 / 두 번째 / 되돌리기 / 전환 도중.
  예) 효과음: 무대 비었다→참여, 참여→내려감(무대 빔), 다른 사람 있는 채 참여·내려감, 방 나가기 × 통화모드/일반모드.
- 수정안이 표의 **모든 칸**에서 맞는지 확인하고 나서 쓴다. 한 칸 고치려다 다른 칸 깨는 수정은 버린다.

## 3. 반복 시나리오를 테스트로 박는다
- 사용자가 겪을 순서 그대로, **최소 3회 반복**하는 테스트를 먼저 쓴다(예: `VoiceTest.joiningAndLeavingTheVoiceChimesEveryTime…`, `RoomSoundsDeviceTest`).
- 실기기에서만 보이는 것(소리 경로 등)은 결정 로직을 분리해 Robolectric으로 검증하고, 그 결정의 근거(플랫폼 동작)는 1번처럼 소스로 확인한다. 확인 수단을 먼저 찾고, 정말 없는 것만 보고에 한 줄.

## 4. 코드는 대체하고, 덧붙이지 않는다
- 고칠 때는 기존 코드를 바꿔 끼운다. 실패한 시도의 코드·주석·옵션은 같은 커밋에서 지운다.
- 커밋 전 `git diff`를 다시 읽고: 늘어난 줄마다 필요한 이유가 있는가? 같은 일을 하는 코드가 두 곳에 있는가? 없애도 되는 매개변수·분기·상수가 있는가?
- 웹과 Android는 같은 규칙을 같은 이름으로(`crowdChange` ↔ `RoomSounds.change`). 한쪽만 고치지 않는다.

## 5. 보고는 확인된 결과만, 짧게
- 한 일, 원인(근거), 테스트 결과. 추측·변명·긴 "확인 못 한 것" 목록 금지.
- 사장님 확인이 필요한 건 정말 이 환경에서 불가능한 것 하나만, 확인 순서와 함께.
