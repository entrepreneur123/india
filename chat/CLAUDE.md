# 랜챗(Yaari) 헌법 — 모든 규칙보다 우선 (사장님 지시)

1. **소분류 → 직렬 처리 → 효율 확인.** 지시를 작은 작업으로 나눠 하나씩 순서대로 끝낸다. 끝낼 때마다 더 짧고 일반적인 식으로 줄일 수 있는지 본다(`x=1→3, x=2→5`를 두 줄로 쓰지 말고 `2x+1` 한 줄). 기존 코드의 비효율도 보이면 줄인다.
2. **끝나면 직접 눌러보고 검증한다.** "아직 확인하지 못했습니다"로 끝내지 않는다 — 중요한 건 내가 확인한다(Playwright·테스트·SQL 실행). 이전 작업과 무관한 새 작업이면 앞 맥락은 짧게 요약하고 토큰을 아낀다.
3. **기존 레이어를 건너뛰는 함수 금지.** 화면이 DB를 직접 건드리거나, 기존 RPC·헬퍼·`_shared`를 우회해 같은 로직을 새로 쓰는 코드가 생겼는지 계속 확인하고 기존 레이어로 되돌린다.
4. **마이그레이션은 관례대로만.** `server/migrations/NNN_name.sql` 다음 번호로 새 파일만 추가하고, 이미 적용된 파일은 고치지 않는다. 재실행해도 안전하게(`if not exists`, `create or replace`), 기존 RLS·권한·이름 규칙을 따른다. 사장님은 바이브코딩 위주라 마이그레이션 오류가 곧 큰 사고다 — 매우 꼼꼼히 검사한다.
5. **중복 API 엔드포인트 금지.** 같은 일을 하는 RPC·edge function·라우트가 둘이면 하나로 합치고 나머지는 지운다. 새로 만들기 전에 기존 것부터 찾는다.
6. **확실하지 않으면 적용하지 않는다.** 먼저 적용하고 나중에 고치는 게 가장 큰 낭비다. 정확성·효율이 최우선.
7. **점검 = 전부 눌러보기.** 새 기능·수정·전체 점검 때 모든 버튼·상태를 시뮬레이션하고 콘솔 에러까지 확인한다. 조금이라도 이상하면 즉시 고친다. 모든 경우의 수를 열어 둔다.
8. **할루시네이션 판단이 안 되면 교차 검증.** 다른 에이전트·공식 문서·실제 소스와 대조해 확실성을 높인다. 지금 하는 일이 무엇을 위한 것인지 늘 인지한다.
9. **웹 먼저.** 웹·모바일 앱을 함께 만들지만 항상 웹부터 만든다. 출시 직전 사장님이 지시하면 그때 웹에 반영된 것을 휴대폰 양식에 맞춰 앱으로 옮긴다(이후 문제는 사장님 지시로 해결).
10. **현재 인터페이스는 깔끔하고 예쁘다 — 크게 바꾸지 않는다.**

# 랜챗(Yaari) 작업 방식 — 하자·슬롭 방지

0.18.4–0.18.6에서 효과음 하나를 추측으로 세 번 고치다 매번 다른 곳이 깨졌다. 같은 일이 다시 없도록 아래 순서를 지킨다.

## 1. 원인을 확정하기 전에는 코드를 고치지 않는다
- 증상을 재현하거나(데모 웹을 Playwright로, Android는 Robolectric 테스트로), 재현이 안 되면 **근거를 직접 읽는다**: 우리 코드의 실제 흐름, 라이브러리 소스·바이트코드(`~/.gradle/caches`의 aar → `javap -c`, `node_modules`), 플랫폼 소스(AOSP).
- "아마 이거겠지"로 고친 커밋 금지. 커밋 메시지·보고에 원인과 근거(파일·줄)를 쓴다.

## 2. 상태가 바뀌는 기능은 표부터 그린다
- 기능이 다른 상태(오디오 모드, 네트워크 연결, 권한, 백그라운드, 로그인)를 건너면 **모든 경우를 표로**: 처음 / 두 번째 / 되돌리기 / 전환 도중 / **빠르게 연타**(쓰로틀·지연·디바운스가 내 동작까지 막지 않는지).
  예) 효과음: 무대 비었다→참여, 참여→내려감(무대 빔), 다른 사람 있는 채 참여·내려감, 방 나가기 × 통화모드/일반모드.
- 수정안이 표의 **모든 칸**에서 맞는지 확인하고 나서 쓴다. 한 칸 고치려다 다른 칸 깨는 수정은 버린다.

## 3. 반복 시나리오를 테스트로 박는다
- 사용자가 겪을 순서 그대로, **최소 3회 반복**하는 테스트를 먼저 쓴다(예: `VoiceTest.joiningAndLeavingTheVoiceChimesEveryTime…`, `RoomSoundsDeviceTest`).
- 실기기에서만 보이는 것(소리 경로 등)은 결정 로직을 분리해 Robolectric으로 검증하고, 그 결정의 근거(플랫폼 동작)는 1번처럼 소스로 확인한다. 확인 수단을 먼저 찾고, 정말 없는 것만 보고에 한 줄.

## 4. 코드는 대체하고, 덧붙이지 않는다
- 고칠 때는 기존 코드를 바꿔 끼운다. 실패한 시도의 코드·주석·옵션은 같은 커밋에서 지운다.
- 커밋 전 `git diff`를 다시 읽고: 늘어난 줄마다 필요한 이유가 있는가? 같은 일을 하는 코드가 두 곳에 있는가? 없애도 되는 매개변수·분기·상수가 있는가?
- 웹과 Android는 같은 규칙을 같은 이름으로(`crowdChange` ↔ `RoomSounds.change`). 한쪽만 고치지 않는다.

## 5. 보고는 확인된 결과만, 짧게
- 한 일, 원인(근거), 테스트 결과. 추측·변명·긴 "확인 못 한 것" 목록 금지.
- 사장님 확인이 필요한 건 정말 이 환경에서 불가능한 것 하나만, 확인 순서와 함께.
